# สรุปผลการทดลอง NSGA-II (EvoSuite)

## วัตถุประสงค์และขอบเขต

ศึกษาการสร้าง JUnit unit tests ด้วยอัลกอริทึม NSGA-II ผ่านเครื่องมือ EvoSuite (เวอร์ชัน 1.2.0) บน Defects4J โดยตรวจความถูกต้องของชุดทดสอบ วัดความครอบคลุมของโค้ด และประเมินการตรวจพบข้อบกพร่อง

หนึ่ง case ในข้อมูลสรุปหมายถึงหนึ่ง Project–Bug ID ไม่ใช่หนึ่ง test method จำนวนกรณีที่เริ่มทดลองจึงต้องแยกจากจำนวนชุดทดสอบที่ประเมินสำเร็จ เช่นเดียวกับที่ใช้ในสรุปผลของ ChatGPT และ GitHub Copilot

|รอบ|search budget|ชุดผลที่ใช้ (run\_id)|
|-|-|-|
|Round 1|150 วินาที/คลาส|02|
|Round 2|60 วินาที/คลาส|03|

ผลของ NSGA-II เป็นส่วนหนึ่งของการเปรียบเทียบร่วมกับ ChatGPT, GitHub Copilot และ Symbolic Execution ดู [ผลเปรียบเทียบทั้ง 4 วิธี](final_comparison.md)

**Round 1 และ Round 2 ใช้ search budget ต่างกันโดยตั้งใจ เป็นคนละ configuration ไม่รวมหรือเฉลี่ยตัวเลขสองรอบนี้เข้าด้วยกัน รายงานทุกค่าแยกตามรอบเสมอ**

## ขั้นตอนและหลักการวัด

1. Checkout โค้ดเวอร์ชัน buggy และ fixed จาก Defects4J แยกกัน
2. เรียก EvoSuite ให้สร้างชุดทดสอบจาก **เวอร์ชัน buggy เท่านั้น** ด้วยอัลกอริทึม `-Dalgorithm=NSGAII`
3. รันชุดทดสอบที่ได้กับทั้งเวอร์ชัน buggy และ fixed
4. วัด line/condition coverage บนเวอร์ชัน fixed และบันทึกผล pass/fail ของทั้งสองเวอร์ชัน
5. จัดกลุ่มผลเป็น `ok` / `generation\_failed` / `not\_evaluable` / `compile\_failed\_b` ตามจุดที่ล้มเหลว (ถ้ามี)

รายละเอียด pipeline, parameter ที่ใช้ และสภาพแวดล้อมอยู่ใน `README.md` / `RUNBOOK.md` ของส่วน NSGA-II

### ข้อควรระวังเรื่องทิศทางการตรวจพบบั๊ก (สำคัญสำหรับการเทียบกับ AI tracks)

EvoSuite สร้างชุดทดสอบจากเวอร์ชัน buggy เพียงอย่างเดียว และบันทึก assertion จาก**พฤติกรรมจริงของเวอร์ชัน buggy เอง** ดังนั้นการตรวจพบบั๊กที่แท้จริงคือกรณีที่ชุดทดสอบ **ผ่านบน buggy แต่ล้มเหลวบน fixed** ซึ่งเป็น**ทิศทางตรงข้าม**กับ ChatGPT/Copilot ที่เขียน assertion จากพฤติกรรมที่ถูกต้องตามที่โมเดลคาดเดา (ล้มเหลวบน buggy แต่ผ่านบน fixed) **ห้ามเทียบค่า fault detection ของสองฝั่งตรง ๆ โดยไม่แปลงให้อยู่ทิศทางเดียวกันก่อน**

## ผลการประเมินชุดทดสอบ

`ok` หมายถึงชุดทดสอบถูกสร้างสำเร็จและมีผล final evaluation ครบทั้งสองเวอร์ชัน ไม่ได้หมายความว่าตรวจพบ bug ทุกกรณี

|รอบ|เริ่มทดลอง (cases)|ประเมินสำเร็จ (ok)|อัตราประเมินสำเร็จ|generation\_failed|not\_evaluable|compile\_failed\_b|
|-|-:|-:|-:|-:|-:|-:|
|Round 1 (150s)|854|789|92.39%|34|31|0|
|Round 2 (60s)|854|669|78.34%|165|17|3|

อัตราประเมินสำเร็จ = จำนวน `ok` ÷ จำนวน cases ที่เริ่มทดลอง × 100

## การตรวจพบข้อบกพร่อง

|รอบ|Cases ที่มีผลวัด|Cases ที่ตรวจพบ fault|อัตราในกลุ่มที่มีผลวัด|ตรวจพบ fault ต่อ cases ที่เริ่มทดลอง|
|-|-:|-:|-:|-:|
|Round 1 (150s)|789|111|14.07%|13.00%|
|Round 2 (60s)|669|95|14.20%|11.12%|

อัตราในกลุ่มที่มีผลวัดใช้ cases ที่มี fault-detection result เป็น denominator ส่วนอัตราต่อ cases ที่เริ่มทดลองแสดงผลสำเร็จของกระบวนการโดยรวม ไม่แทนผลที่ไม่มีค่าด้วยข้อสรุปว่าชุดทดสอบตรวจไม่พบ fault (ทิศทางการตัดสินตามหัวข้อก่อนหน้า)

## ความครอบคลุมของโค้ด

|รอบ|Cases ที่มี line coverage|Line coverage เฉลี่ย|Cases ที่มี condition coverage|Condition coverage เฉลี่ย|
|-|-:|-:|-:|-:|
|Round 1 (150s)|789|54.27%|786|43.97%|
|Round 2 (60s)|669|49.61%|666|39.19%|

Coverage ราย case = จำนวนที่ครอบคลุม ÷ จำนวนทั้งหมด × 100 ตารางแสดงค่าเฉลี่ยราย case บน fixed version เฉลี่ยเฉพาะค่าที่มีจริง ไม่ใช่การรวม covered/total ของทุก case ก่อนหาร (หลักการเดียวกับ ai\_summary.md)

Line coverage วัดจาก EvoSuite criterion `LINE` (statement-level) และ condition coverage วัดจาก criterion `BRANCH` ของ EvoSuite — ใช้ชื่อ Line/Condition Coverage ให้ตรงกับชื่อที่ใช้ในสรุปของ AI tracks เพื่อให้เทียบกันได้ แม้เครื่องมือเบื้องหลังจะเรียกชื่อ criterion ต่างกัน

## จำนวนชุดทดสอบที่สร้าง

ยังไม่มีตัวเลขจำนวน test method ต่อ case ในข้อมูลชุดนี้ มีเพียงไฟล์ archive (`tests.tar.bz2`) ต่อ case ที่ประเมินสำเร็จ การนับจำนวน test method ต้องแกะไฟล์ `.java` ในแต่ละ archive เพิ่มเติมก่อนจึงจะรายงานตัวเลขนี้ได้

## วิเคราะห์ผล

อัตราตรวจพบ fault ในกลุ่มที่มีผลวัดใกล้เคียงกันมากระหว่างสองรอบ (14.07% ที่ budget 150 วินาที เทียบกับ 14.20% ที่ 60 วินาที) แม้ budget ต่างกัน 2.5 เท่า บ่งชี้ว่าการเพิ่ม budget ในช่วงนี้ไม่ได้ทำให้อัตราตรวจพบ fault เพิ่มขึ้นอย่างมีนัยสำคัญ

ในทางกลับกัน อัตราการประเมินสำเร็จต่างกันชัดเจน (92.39% ที่ budget 150 วินาที เทียบกับ 78.34% ที่ 60 วินาที) การลด budget ทำให้สัดส่วน `generation\_failed` เพิ่มขึ้นจาก 4.0% เป็น 19.3% ของ cases ทั้งหมด ส่งผลให้อัตราตรวจพบ fault ต่อ cases ที่เริ่มทดลอง (ซึ่งนับรวมความล้มเหลวด้วย) ลดลงจาก 13.00% เหลือ 11.12% ทั้งที่อัตราในกลุ่มที่มีผลวัดแทบไม่เปลี่ยน

Coverage เฉลี่ยลดลงตามทิศทางที่คาดจาก budget ที่ลดลง (line coverage จาก 54.27% เหลือ 49.61%, condition coverage จาก 43.97% เหลือ 39.19%) แต่ขนาดการลดลงไม่มากเท่าสัดส่วน budget ที่ลดลง (60% ของ budget เดิม)

## ปัญหาและข้อจำกัด

* รันเพียง seed เดียว (seed=11) ในทั้งสองรอบ ไม่ได้วัดความแปรปรวนข้าม seed ตัวเลขที่รายงานจึงเป็นผลจาก run เดียวต่อ configuration
* Round 1 และ Round 2 เป็นคนละ configuration (budget ต่างกัน) โดยตั้งใจ ห้ามเฉลี่ยรวมกัน ต้องรายงานแยกเสมอตามที่แสดงในทุกตารางข้างต้น
* ทิศทางการตัดสิน fault detection ตรงข้ามกับ AI tracks ตามที่อธิบายไว้ในหัวข้อ "ข้อควรระวังเรื่องทิศทาง" ด้านบน ต้องแปลงให้อยู่ทิศทางเดียวกันก่อนเปรียบเทียบข้ามวิธีเสมอ
* Round 2 รวมผลจาก 2 เครื่องที่อาจมี environment ต่างกันเล็กน้อย (เวอร์ชัน Java patch, สเปกเครื่อง) ซึ่งอาจมีผลต่อความแปรปรวนของเวลาและผลลัพธ์บางส่วน
* ยังไม่มีจำนวน test method ต่อ case ต้องแกะจาก archive เพิ่มเติมก่อนรายงานตัวเลขนี้ได้
* `generation\_failed` ที่เพิ่มขึ้นมากใน Round 2 ยังไม่ได้แยกสาเหตุย่อย (เช่น timeout เทียบกับ error ประเภทอื่น) ในข้อมูลชุดนี้ การวิเคราะห์สาเหตุเชิงลึกต้องเปิดดู log รายกรณีเพิ่มเติม

## สิ่งที่เรียนรู้

Budget ของ search algorithm ไม่ได้ส่งผลต่ออัตราตรวจพบ fault โดยตรงเท่ากับที่ส่งผลต่อ**อัตราความสำเร็จในการสร้างชุดทดสอบ** การเพิ่ม budget ช่วยลดสัดส่วน case ที่สร้าง test ไม่สำเร็จได้ชัดเจนกว่าการเพิ่มโอกาสตรวจพบ fault ในกลุ่มที่สร้างสำเร็จแล้ว ดังนั้นเมื่อประเมินประสิทธิภาพของ search-based test generation จึงต้องแยกพิจารณา "ความสามารถในการสร้างชุดทดสอบให้เสร็จ" ออกจาก "ความสามารถของชุดทดสอบที่สร้างสำเร็จในการตรวจพบบั๊ก" เช่นเดียวกับหลักการที่ใช้ประเมิน AI tracks
