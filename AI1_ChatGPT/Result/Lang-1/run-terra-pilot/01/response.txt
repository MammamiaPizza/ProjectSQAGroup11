## Scope and test target

The supplied class is `org.apache.commons.lang3.math.NumberUtils`. It is a stateless utility class with a public no-argument constructor and static utility methods.

The supplied bug report, **LANG-747**, specifically concerns:

```java
public static Number createNumber(final String str)
```

Therefore, the primary regression tests should target `createNumber(String)`, especially hexadecimal inputs whose numeric value exceeds `Integer.MAX_VALUE` despite having no more than eight hexadecimal digits.

No production changes should be made.

## 2. Input types and valid input ranges

### `createNumber(String)`

Input type: `String`, including `null`.

Supported categories, according to the supplied source documentation and implementation:

- Decimal integers:
  - `"0"`, `"1"`, `"-1"`
  - Integer, Long, and BigInteger-sized values.
- Hexadecimal integer syntax:
  - `"0x..."`, `"0X..."`
  - `"-0x..."`, `"-0X..."`
  - `"#..."`
  - `"-#..."`
- Octal integral syntax:
  - Leading zero, such as `"0777"`.
- Decimal floating-point syntax:
  - `"1.5"`, `"1."`, `".5"` where accepted by the delegated parsers.
- Scientific notation:
  - `"1e3"`, `"1E3"`, `"1.2e-3"`.
- Type suffixes:
  - `f`, `F`, `d`, `D`, `l`, `L`.
- `null`, which must return `null`.
- Blank input, which must throw `NumberFormatException`.
- Invalid numeric syntax, which must throw `NumberFormatException`.

For hexadecimal values, the important representable ranges are:

| Result type | Positive hexadecimal magnitude range |
|---|---|
| `Integer` | `0x0` through `0x7FFFFFFF` |
| `Long` | `0x80000000` through `0x7FFFFFFFFFFFFFFF` |
| `BigInteger` | Values outside signed `long` range |

For negative hexadecimal values, valid limits differ because the signed minimum is one larger in magnitude:

| Result type | Negative hexadecimal boundary |
|---|---|
| `Integer` | `-0x80000000` is representable as `Integer.MIN_VALUE` |
| `Long` | `-0x8000000000000000` is representable as `Long.MIN_VALUE` |

The exact handling of all negative hex boundary cases should be confirmed against the authoritative fix or existing test suite if tests beyond the supplied bug description are desired.

Valid numeric range is the corresponding Java primitive parser range:

### `createBigInteger`

Input type: `String`, including `null`.

Supported prefixes in the implementation:

- `"0x"` lower-case only, as implemented
- `"#"`

Potential implementation/documentation inconsistency:


The same lower-case condition is repeated. Upper-case `"0X"` is not recognized by this method, despite `createNumber` recognizing `"0X"` as a hexadecimal prefix. This is outside the supplied LANG-747 report, but it is a reachable behavior worth noting for broader testing.

### `createBigDecimal`

## 3. Conditions and reachable branches

## `createNumber(String)` branch structure

The most relevant branches for LANG-747 are the hexadecimal-prefix path:

1. `str == null`
   - Returns `null`.

2. `StringUtils.isBlank(str)`
   - Throws `NumberFormatException`.

3. Hexadecimal-prefix recognition:
   - `"0x"`
   - `"0X"`
   - `"-0x"`
   - `"-0X"`
   - `"#"`
   - `"-#"`

4. Hexadecimal digit-count selection:
   ```java
   if (hexDigits > 16) {
       return createBigInteger(str);
   }
   if (hexDigits > 8) {
       return createLong(str);
   }
   return createInteger(str);
   ```

5. Non-hex processing:
   - Decimal-point detection.
   - Exponent detection.
   - Suffix detection (`L/l`, `F/f`, `D/d`).
   - Integral type escalation:
     `Integer` → `Long` → `BigInteger`.
   - Floating type escalation:
     `Float` → `Double` → `BigDecimal`.
   - Precision routing based on digits after the decimal point:
     - ≤7 decimal digits: try `Float`.
     - 8–16 decimal digits: try `Double`.
     - >16 decimal digits: `BigDecimal`.

### LANG-747 faulty branch

A hexadecimal literal with exactly eight digits is always routed to:

```java
return createInteger(str);
```

This is wrong when the hexadecimal magnitude exceeds the positive signed `int` range.

Examples:

- `"0x7FFFFFFF"` fits in `Integer`; current routing is valid.
- `"0x80000000"` has eight hex digits but exceeds `Integer.MAX_VALUE`; it must not be forced through `createInteger`.
- `"0xFFFFFFFF"` has eight hex digits but represents `4294967295`, which requires `Long`.

The current buggy source will invoke `Integer.decode` for the latter two positive values, causing `NumberFormatException`.

### Other key reachable branches

- Hex values with 9–16 digits are sent to `createLong`.
- Hex values with more than 16 digits are sent to `createBigInteger`.
- Decimal integral values attempt `Integer`, then `Long`, then `BigInteger`.
- Decimal floating values select among `Float`, `Double`, and `BigDecimal`.
- Type-qualified long values reject decimal/exponent forms.
- Invalid suffixes and malformed exponent forms throw `NumberFormatException`.

## 4. Normal, boundary, invalid, null, and exceptional cases

## Required LANG-747-focused cases

These are the highest-value regression cases.

### Normal hexadecimal integer case

- Input: `"0x7FFFFFFF"`
- Expected result:
  - type: `Integer`
  - value: `Integer.MAX_VALUE` (`2147483647`)
- Purpose: establishes the largest positive hexadecimal value that still fits in `Integer`.

### Boundary just above `Integer.MAX_VALUE`

- Input: `"0x80000000"`
- Expected result:
  - type: `Long`
  - value: `2147483648L`
- Purpose: exact transition from `Integer` to `Long`.

### Eight-digit hexadecimal value requiring `Long`

- Input: `"0xFFFFFFFF"`
- Expected result:
  - type: `Long`
  - value: `4294967295L`
- Purpose: direct reproduction of the reported defect: an eight-digit hexadecimal value must not be assumed to fit `Integer`.

### Prefix variants

The implementation expressly supports these prefixes, so representative coverage should include:

- `"0XFFFFFFFF"` → `Long` with value `4294967295L`
- `"#FFFFFFFF"` → `Long` with value `4294967295L`

The expected result follows the documented prefix support and the same numeric-range requirement described in LANG-747.

### Existing behavior control case

- Input: `"0x100000000"`
- Expected:
  - type: `Long`
  - value: `4294967296L`
- Purpose: validates that the existing `hexDigits > 8` Long-routing branch continues to work.

## Useful extended boundaries

These are logically related to hex type selection but go beyond the explicit supplied bug text.

- `"0x7FFFFFFFFFFFFFFF"`

## 8. Behaviors related to LANG-747 that should be tested

The regression tests should verify all of the following:

1. **Eight hex digits alone must not determine `Integer` suitability.**
   - A positive eight-digit hex value can exceed `Integer.MAX_VALUE`.

2. **`createNumber("0x80000000")` must return a `Long`.**
   - Expected numeric value: `2147483648L`.

3. **`createNumber("0xFFFFFFFF")` must return a `Long`.**
   - Expected numeric value: `4294967295L`.

4. **Existing valid `Integer` hex behavior is retained.**
   - `createNumber("0x7FFFFFFF")` remains an `Integer`.

5. **Supported hexadecimal prefix variants should receive equivalent range handling.**
   - At minimum, consider `"0XFFFFFFFF"` and `"#FFFFFFFF"`.
   - The source explicitly recognizes these prefix forms in `createNumber`.

6. **No `NumberFormatException` should be thrown for valid, positive hexadecimal values that fit in `long`.**
   - This is the observed failure mechanism in the buggy implementation.

A test that only verifies numeric equality is insufficient: it should also assert the concrete returned type. For example, an expected `Long` must not merely be numerically equal to some other `Number`; the type-selection behavior is part of the API behavior under test.
